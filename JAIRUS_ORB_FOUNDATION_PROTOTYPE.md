# JAIRUS ORB FOUNDATION PROTOTYPE

First technical/visual prototype for the new Jairus orb, built per
`JAIRUS_ORB_VFX_TECHNICAL_ARCHITECTURE.md`. Strictly scoped to: EnergyModel +
procedural core + shader architecture + debug controls + a transparent-window
presentation test + a minimal distortion/refraction experiment + baseline
performance measurement. No rings, wisps, particle populations, fragments,
symbol system, final post-processing, full state system, or real Jairus
integration were built — all explicitly deferred per the task brief.

Everything here lives in a new, isolated Godot 4.7.2 project at
`prototype/orb_foundation/`, not wired into `main.py`'s renderer launch path
and not connected to the real `bridge.py` WebSocket. No existing tracked file
in the repository was modified — `git status` shows only new, untracked
files (this document, the architecture doc from the prior task, and
`prototype/`).

## 1. What was implemented

- **EnergyModel** (`energy_model.gd`, autoload singleton): owns 9 shared
  float parameters, smooths each toward a target at its own rate, and pushes
  all 9 to Godot's global shader uniform mechanism every frame.
- **Procedural core** (`core.gd` + `core.gdshader` + `energy_common.gdshaderinc`):
  a geodesic icosphere built at runtime (no imported mesh), displaced in the
  vertex shader by two domain-warped noise configurations blended by
  `core_morph`, with a finer secondary layer driven by `turbulence`, a
  finite-difference-recomputed normal, Fresnel rim shading, and a
  near-white/maroon/gold palette.
- **Debug controls** (`debug_ui.gd`): plain sliders for all 8 continuous
  parameters, a "Trigger Pulse" button, and a camera-drift toggle, built in
  code as disposable tooling.
- **Camera** (`camera_rig.gd`): a `Camera3D` under a drift rig, toggleable,
  amplitude modulated slightly by `activity`.
- **Minimal environment** (`main.tscn`'s `WorldEnvironment` + one
  `OmniLight3D`): just enough to read silhouette/material/Fresnel/deformation.
- **Presentation test**: `main.tscn` run as a borderless, always-on-top,
  per-pixel-transparent window, screenshotted at the real OS level.
- **Distortion/refraction experiment**: a separate, standalone scene
  (`distortion_test.tscn` + `lensing_test.gdshader`) testing a
  `hint_screen_texture` lensing shell over a marker sphere, independent of
  EnergyModel.
- **Performance logging** (`perf_monitor.gd`): samples Godot's `Performance`
  singleton every second, writes real numbers to `perf_log.txt` and stdout.

## 3. EnergyModel architecture

`energy_model.gd` is an autoload singleton (`/root/EnergyModel`). It owns
`target_*` values (set by the debug UI) and `current_*` values (exponentially
smoothed toward the target every `_process()`, at one of three rates —
fast/medium/slow, matching the architecture doc's guidance), plus a
`current_pulse` that jumps to 1.0 on `trigger_pulse()` and decays linearly.
Every frame it calls `RenderingServer.global_shader_parameter_set()` for all
9 parameters. No consumer (currently just `core.gdshader`, via
`energy_common.gdshaderinc`) holds a reference to `EnergyModel` or to each
other — they only declare the matching `global uniform float` and read it.
This is the "one parameter model, many independent visual systems" structure
the architecture doc's section 12 asked for, and it costs nothing extra to
add a second consumer (e.g. a future wisp shader) later.

Of the 9 parameters, this prototype's shader actually **consumes**
`energy_intensity`, `energy_activity`, `energy_turbulence`,
`energy_coherence`, `energy_core_morph`, `energy_pulse`, and
`energy_symbol_reveal`. `energy_field_strength` and
`energy_particle_activity` are declared, registered as global shader
uniforms, smoothed, and pushed every frame exactly like the others, but
nothing reads them yet — there's no field or particle system in this
prototype. This matches the task brief's explicit "the prototype does not
need all parameters to visually affect something yet."

## 4. Shader architecture

Three small files instead of one large shader, per the architecture doc's
own recommendation:

- `energy_common.gdshaderinc` — the 9 global uniform declarations, the
  Fresnel function, and the noise primitives (`hash13`, `value_noise3`,
  `fbm3`, `domain_warped_fbm`). Anything that wants these just `#include`s
  this file.
- `core.gdshader` — the only shader that currently exists for a visible
  object. Vertex stage does the displacement/morph/normal-recompute;
  fragment stage does the palette/Fresnel/gold-accent logic.
- `lensing_test.gdshader` — deliberately standalone, does **not** include
  `energy_common.gdshaderinc` and is not driven by EnergyModel, because the
  distortion experiment (section 9 below) is an isolated technical test, not
  part of the core visual system.

## 5. Core geometry

`core.gd` builds a geodesic icosphere procedurally (standard recursive
icosahedron subdivision with cached, deduplicated edge midpoints — no
imported mesh, no external DCC tool). Subdivision level 4 was chosen after
comparing levels 3 and 5 by eye: level 3 (642 vertices) visibly faceted under
this shader's displacement amplitudes; level 5 (10242 vertices) looked
identical to level 4 while costing more per-vertex shader work. Level 4
measured **2562 vertices / 5120 triangles** (confirmed via `perf_log.txt`,
not estimated).

## 6. Morphing approach

**Updated in the core redesign pass — see section 17.** `core.gdshader`
blends two noise *configurations* by `core_morph`. Configuration A is now a
coarse, low-frequency, **2-octave** fbm (`fbm_coarse`, missing the original
3-octave `fbm3`'s finest p*4 octave entirely) domain-warped by a narrower
warp range than before — tuned for "a few large deliberate lobes" rather
than the original's finer, more uniformly bumpy surface. Configuration B is
no longer a ridge transform of the same fbm; it's a genuine **cellular/
Voronoi basis** (`worley3_f1f2`'s F2-F1 edge metric, `domain_warped_voronoi`
in `energy_common.gdshaderinc`), which produces sharp-creased, flat-ish
plates instead of the ridge transform's rounded bumps. `coherence` still
scales the domain-warp strength down (more coherence = less chaotic warping
in both configurations), though this range was narrowed as part of taming
configuration A's lobes, with a real side effect — see section 17.
`turbulence` still scales a separate, finer secondary noise layer's
contribution. The vertex shader still recomputes the normal via finite
differences (sampling the same displacement function at two nearby
tangent-offset points) rather than reusing the sphere's analytic normal,
since the analytic normal would light the surface as if undisplaced and
hide the deformation. The palette (maroon vs. white) now reads from its own,
separate, higher-frequency noise sample rather than from the displacement
signal itself — see section 17 for why. See section 17 for how this
actually looks now; section 11 below is the original pass's findings,
kept for the record.

## 7. Debug controls

`debug_ui.gd` builds a `PanelContainer` with one label+`HSlider` row per
continuous parameter (Intensity, Activity, Turbulence, Coherence, Core
Morph, Field Strength, Particle Activity, Symbol Reveal), a "Trigger Pulse"
button, and a "Camera Drift" `CheckButton`, entirely in code (no hand-laid-out
`.tscn` UI). Verified working by direct visual test (section 11's parameter
sweeps were done by editing `EnergyModel`'s initial target values and
re-running, which exercises the exact same code path the sliders call).

## 8. Transparent-window result — FAILED, and this contradicts the task's stated prior validation

The task briefing stated this exact combination (Mobile/Vulkan renderer +
borderless/transparent/always-on-top/per-pixel-transparency window) had
already been stress-tested and confirmed stable **on this machine**, and
asked me to apply it directly and only re-verify, not rediscover it. I did
apply it directly, carrying forward the same renderer method and window
flags from `archive/orb_v1/godot_project/project.godot` byte-for-byte. **The
re-verification failed**: real desktop content does not show through the
window at all.

What I observed, with real evidence, not assumption:

- `main.tscn` run windowed (not headless) via the same Godot executable
  `main.py` is configured to launch (`Godot_v4.7.2-stable_win64.exe`,
  v4.7.2-stable).
- `DisplayServer.window_get_flag(DisplayServer.WINDOW_FLAG_TRANSPARENT)`
  reports `true` at runtime — the OS-level window flag is genuinely set.
- A real OS-level screenshot (`System.Drawing.Graphics.CopyFromScreen` over
  the live desktop, same method the archived investigation used) shows the
  window as a **flat, uniform gray rectangle**, not the desktop behind it.
  Sampling actual pixels confirms this numerically: inside the window,
  `RGB(78,78,78)`; at the same screen height just outside the window,
  `RGB(33,33,33)`/`RGB(38,38,38)` (the real, darker desktop). These do not
  match — the window is opaque, not compositing with the desktop.
- I tried three additional, specifically-documented candidate fixes before
  concluding this is a real, unresolved problem rather than a missed
  setting:
  1. Added `rendering/viewport/transparent_background=true` (a distinct
     project setting from `environment/defaults/default_clear_color`, and
     absent from the archived project's `project.godot` despite being
     documented as required) — no change.
  2. Switched the base renderer method between `mobile` and
     `gl_compatibility` (a community-reported, version-spanning Godot bug,
     Godot issue #103456, describes exactly this failure — transparent
     window shows opaque black/gray under `forward_plus`/`mobile` on
     Windows 11 + Vulkan + NVIDIA laptop GPUs, "resolved" by switching to
     `gl_compatibility`) — no change; both renderer methods produced an
     opaque window (a different flat shade of gray between the two, but
     still opaque, confirmed by the same pixel-sampling method).
  3. Disabled debanding (`rendering/anti_aliasing/quality/use_debanding=false`,
     a separately-documented cause of exactly this failure mode) and
     disabled V-Sync — no change.
- The distortion experiment (section 9) independently corroborates that the
  *whole* window — not just the debug UI panel — is opaque: the void area
  around the lensing shell, inside the window but outside any 3D object, is
  also the same flat gray, not the desktop.

I stopped escalating after these three targeted, documented checks because
further root-causing this (this looks like it may be a genuine Windows/DWM
compositor or driver-level interaction with Godot's Vulkan/OpenGL swapchain
alpha output, not a Godot project setting) is a distinct, open-ended
investigation of its own, not something this foundation prototype's scope
should absorb.

**This is a real, reproducible negative result, not a rediscovery I chose to
skip** — I did attempt the "smaller confirmatory check" the task asked for,
it did not confirm, and I'm reporting that honestly rather than asserting the
prior validation still holds. Whatever produced a working transparent window
in the archived investigation's screenshot, it is not reproducible from this
fresh project's otherwise-identical settings on this machine today. This is
the single most important open finding in this prototype: the
"floating desktop artifact" presentation model (architecture doc's Question
D) is currently **unconfirmed on this machine**, not confirmed as previously
believed.

## 8a. Follow-up root-cause investigation (diagnostic-only pass)

A dedicated follow-up (no shader/geometry/EnergyModel changes — diagnostic
only) checked the four candidates recommended in section 15 in order, on
this same machine:

1. **Ran the archived project itself, completely unmodified**
   (`archive/orb_v1/godot_project/`, `orb_scene.tscn`, launched exactly as
   `main.py`'s `_try_launch_godot()` does it —
   `Godot_v4.7.2-stable_win64.exe --path <project>`). Result: **it also
   fails today.** A real screenshot shows the orb rendering correctly
   (rings, plates, glow, particles all visible — the Godot content itself
   is fine), but the window background is the same flat opaque gray as the
   prototype, not the real desktop. Pixel-sampled: inside the window
   `RGB(91,91,91)`; the real desktop at the same height, just outside the
   window, `RGB(49,49,49)`/`RGB(51,51,51)`. This is decisive: **the
   archived project's transparency is broken too, unmodified, today** —
   this is not a prototype-configuration difference.
2. **Config diff** (`archive/orb_v1/godot_project/project.godot` vs.
   `prototype/orb_foundation/project.godot`): the settings that actually
   matter for transparency (`window/size/borderless`, `window/size/
   transparent`, `window/size/always_on_top`, `window/per_pixel_
   transparency/allowed`, `renderer/rendering_method`) are identical.
   The prototype additionally sets `rendering/viewport/transparent_
   background`, disables debanding, and disables V-Sync — settings the
   archived project *doesn't* have at all. If anything, the prototype's
   config is a superset aimed at *more* transparency support, not less.
   Given step 1, this is moot as an explanation anyway.
3. **Editor-binary run vs. exported `.exe`**: only the editor-binary-run
   path was tested (both for the archived project and the prototype), via
   `Godot_v4.7.2-stable_win64.exe --path <project>`. No export templates
   are installed in this Godot install (`%APPDATA%\Godot\export_templates\`
   is empty), so a true exported `.exe` could not be built to test as a
   separate variable. This is not a gap in the operative question, though:
   `main.py`'s `_try_launch_godot()` launches Godot exactly the same way I
   tested (`subprocess.Popen([exe_path, "--path", _GODOT_PROJECT_PATH])`) —
   there is no exported `.exe` in this project's actual production launch
   path, so the editor-binary-run result is the representative one for how
   Jairus would really use this.
4. **Windows/driver state check**: Windows 11 Home Single Language, build
   26200 (originally installed 2025-11-15, so not a recent reinstall);
   NVIDIA driver package dated 2026-08-24 (predates the archived
   investigation's own Sept 13-14 timestamps, so the GPU driver itself did
   not change across this window). However, Windows Update history shows
   **KB5129195 (a Security Update) installed 2026-09-15** — squarely
   between the archived investigation's last "confirmed working" evidence
   (`orb_controller.gd` last modified 2026-09-14 22:14,
   `ORB_RENDERER_INVESTIGATION.md`'s screenshot-verified section 9 dated
   2026-09-13) and today's testing (2026-09-16, both showing the failure).
   Two other updates (KB5124007, KB5126052) landed 2026-09-10, before the
   archived investigation's own successful test, so they're not
   implicated. **KB5129195 is currently the single most concrete lead**:
   it is the only system change identified that lands inside the exact
   window between "last known working" and "now confirmed broken."

**Verdict: this is an environment regression, not a prototype-configuration
difference.** The archived project — untouched, unmodified, same machine —
no longer reproduces its own previously-documented working transparent
window. Whatever changed, changed underneath both projects, not because of
anything different about how the new prototype was configured. The fix (if
one exists without an engine/OS update) is not "add a missing Godot
setting" — every setting the archived project used is already present and
unchanged. This should be tracked as a Windows/driver-level issue (most
likely candidate: KB5129195, installed 2026-09-15), not as a Godot project
configuration bug, and re-checked after any further Windows update or
NVIDIA driver change on this machine.

## 9. Distortion/refraction result

Ran the standalone `distortion_test.tscn`: a bright magenta marker sphere
behind a semi-transparent shell using a `hint_screen_texture`-based
view-space-normal offset (the standard technique). Real screenshot result:

- The shell shows the marker sphere (Godot's own rendered content) roughly
  where expected, with no distinguishable warp beyond the shell's own
  silhouette at this test's geometry/strength settings.
- The area of the shell/window that does **not** overlap the marker in
  screen space shows flat black — Godot's own internal clear color, not the
  desktop.
- This is consistent with, and does **not** contradict, the already-known
  finding cited in the task's additional context: `SCREEN_TEXTURE`/
  `hint_screen_texture` only ever captures Godot's own rendered frame,
  never the real OS-composited desktop. I did not re-litigate that
  conclusion from scratch — this experiment specifically checked same-scene
  lensing behavior, and confirms it operates on Godot's own content only.
- Given section 8's finding, "the desktop doesn't show through the window
  at all right now" is a more fundamental problem than "refraction can't see
  the desktop" — the latter was already expected/documented; the former
  was not.

## 10. Performance measurements

Measured, not estimated, via `perf_monitor.gd` writing to `perf_log.txt`
(also reproduced in stdout), running `main.tscn` windowed at its real
configured resolution:

- **Godot version**: 4.7.2-stable (official).
- **Viewport / window size**: 640×640 (the configured resolution — no
  scaling applied).
- **GPU**: NVIDIA GeForce RTX 3060 Laptop GPU. Renderer: Forward Mobile via
  Vulkan 1.4.351 (also tested under Compatibility/OpenGL 3.3.0 — see section 8).
- **Core mesh**: 2562 vertices, 5120 triangles.
- **Draw calls**: 37 (whole scene — core, debug UI, everything).
- **Primitives/frame**: 6808.
- **Video memory used**: ~21–26 MB (varied slightly run to run).
- **Frame time / FPS**, steady-state across multiple runs: roughly
  **5–6.5 ms/frame (~1800–2000 FPS)**, uncapped (V-Sync did not appear to be
  throttling this window in this configuration — first sample each run was
  slower, ~4.7–10 ms, consistent with a one-time shader-compile/startup cost,
  then it settled into the range above).

This is a trivially cheap scene for this GPU — the core alone is nowhere
near a bottleneck at this vertex count and this renderer. No conclusions
about the *eventual* full orb's performance should be drawn from this
number; it only establishes that today's single-object foundation has large
headroom before the rest of the visual ecosystem (rings, wisps, particles,
etc.) gets added.

## 11. Visual observations (original pass — superseded by section 17)

**This section describes the original core (pre-redesign). It is kept for
the historical record. Section 17 has the current state's findings and is
the one to read for "does the core look right today."**

Evaluated by running the real window (not just the editor viewport) and
inspecting real screenshots, across several parameter combinations by
editing `EnergyModel`'s initial values and re-running (functionally
identical to moving the debug sliders).

**At default/idle-like parameters** (intensity 0.35, activity 0.25,
turbulence 0.2, coherence 0.6, core_morph 0): the core reads as a smooth,
gently dented sphere — closer to a soft "marshmallow" or worn stone than
anything geometric or alien. The maroon/white palette contrast is barely
visible; the surface reads as almost uniformly light gray/white.

**Pushed hard** (intensity 0.6, activity 0.6, turbulence 0.9, coherence 0.9,
core_morph 1.0 — the ridged configuration at near-maximum): the surface
develops a dense, small-scale bumpy/cellular texture — closer to coral,
cauliflower, or a golf ball than to a geometric/crystalline alien artifact.
It is clearly *more active-looking* than the default, but the ridge
transform on smooth value noise produces rounded cellular bumps, not
angular facets. This run was also overexposed (too bright), further washing
out the maroon/white contrast.

**Coherence isolated** (turbulence 0.8, core_morph 0.5, coherence swept from
0.05 to 0.95, intensity fixed at 0.35): there **is** a clearly observable
difference — low coherence produces larger, more irregular warty bumps and
a rougher silhouette; high coherence is visibly smoother and more uniform at
the same turbulence. This is a genuine, working implementation of the
"coherence = organized vs. chaotic, independent of turbulence" requirement.

**Gold/symbol-reveal isolated** (default parameters, symbol_reveal = 1.0):
produces small, sparse, scattered warm-gold speckles across the surface —
restrained, not a wash of gold across the object. This is the one area that
behaved exactly as intended on the first real test.

**Direct answers to the task's required questions:**

- **Does it feel designed?** Not yet. It currently reads as a natural/
  organic deformed sphere, not a designed artifact.
- **Does deformation feel like intelligent morphing?** Partially — `core_morph`
  and `turbulence` do visibly change the surface character (smooth vs.
  cellular), so the mechanism works, but neither endpoint currently looks
  "intelligent" — one looks like a rock, the other like coral.
- **Does it look alien without becoming random?** No. At low turbulence it
  looks like a natural object, not alien; at high turbulence it looks
  textured/organic (cellular), not alien or random-looking in a "computational"
  sense — it doesn't yet suggest information processing.
- **Does the maroon+white combination produce depth?** Not convincingly.
  The maroon rarely reads clearly against the near-white; the object mostly
  looks uniformly pale.
- **Does emission enhance rather than flatten?** At default intensity, the
  object looks reasonably dimensional (the light source + Fresnel give some
  shape read). At high intensity it overexposed and flattened detail.
- **Does Fresnel improve the silhouette?** Present and functioning (the
  math is in place and confirmed via code review of what's being computed),
  but not strongly visible in these screenshots — it needs either a
  stronger power/weight or a darker base material to read clearly against
  this near-white palette.
- **Can the object clearly become more/less active?** Yes — turbulence,
  core_morph, and coherence each visibly change the surface, and this was
  confirmed by direct comparison screenshots, not assumed.

## 12. Problems encountered

1. **Transparent window does not show the real desktop**, despite following
   the task's specified "already validated" configuration exactly, and
   despite trying three further documented candidate fixes. See section 8.
   This is the most significant problem found in this prototype.
2. **The core does not currently read as "alien geometric computational
   intelligence."** See sections 11 and 13 — honest answer, not softened.
3. High-turbulence/high-intensity settings overexposed the material,
   washing out the palette hierarchy the brief asked for.
4. Godot's default project run (no `--quit-after`) ran at very high,

   affected how the performance/presentation tests had to be run.

## 13. What worked

- EnergyModel's shared-parameter architecture: works exactly as designed.
  Every value smooths correctly, pushes to global shader uniforms, and the
  shader consumes them with zero direct coupling to EnergyModel itself.
- The shader-include split (`energy_common.gdshaderinc` shared by future
  shaders) works and kept `core.gdshader` from becoming a monolith.
- Procedural icosphere generation at runtime: correct vertex/triangle counts,
  no seams, no external asset dependency.
- `coherence`'s organized-vs-chaotic effect is real and visually confirmed,
  independent of `turbulence`.
- The restrained-gold `symbol_reveal`/`pulse` accent channel behaves exactly
  as specified: sparse, small, never washing the object gold.
- Baseline performance is a non-issue at this stage: enormous headroom on
  this GPU for a single procedural object at this vertex count.
- The distortion experiment's finding is consistent with (does not
  contradict) the already-established "no real desktop refraction" fact.

## 14. What failed

- **The core's visual identity (original pass).** Neither the default nor

  instruction, I'm reporting this as not satisfying the brief rather than
  describing it as a success. **Addressed in the redesign pass — see
  section 17. Substantially improved, not fully resolved either.**
- The maroon/near-white palette contrast is too weak to read as intended at
  most tested settings. **Also addressed in section 17** — the fix needed
  was more involved than a color/power tweak; see that section for why.

## 17. Core redesign — second pass (coarser deformation + Voronoi + palette fix)

A follow-up task implemented this document's own section 15 recommendation

### A testing gotcha worth recording

Parameter sweeps in this pass initially tried editing `project.godot`'s
`[shader_globals]` initial values, the way `core.gdshader`'s own tunable
uniforms are edited. **This does not work for the `energy_*` parameters**:
`energy_model.gd`'s `_process()` runs from frame 1 and unconditionally
pushes its own hardcoded `target_*`/`current_*` defaults to the global
shader uniforms every frame, overwriting whatever `project.godot` set within
the first frame or two — regardless of what `[shader_globals]` says. Several
early comparison screenshots in this pass were captured this way and were
silently testing the *wrong* parameter values (e.g., a "core_morph = 1.0"
test that actually rendered at the hardcoded default, 0.0). This was caught
by comparing debug-UI slider positions against intended values, not assumed
away. The correct way to test a value that isn't the coded default, without
touching `debug_ui.gd` or `energy_model.gd`'s architecture, is to
temporarily edit `energy_model.gd`'s `target_*` initializers, capture, then
revert — the same method this document's own section 11 used originally
("functionally identical to moving the debug sliders"). Every value in
`energy_model.gd` was reverted to its original default before this pass
finished; `git diff` on that file is empty.

### Stage 1 — coarser base deformation alone

Configuration A's frequency dropped (1.6 → 0.85) and switched from `fbm3`
(3 octaves, up to p*4) to a new `fbm_coarse` (2 octaves, up to p*2,
weighted 0.7/0.3 toward the lower one) — fewer octaves matters more here
than frequency alone, since octaves are what add small-scale detail on top
of the base shape. `displacement_amplitude` raised (0.18 → 0.34) so the
resulting lobes read as pronounced, and coherence's warp range narrowed
(1.4-0.35 → 0.85-0.25) so warping doesn't dissolve the now-larger lobes back
into mush. Result, real screenshot, same camera as the original baseline:
genuinely fewer, larger, more deliberate-looking bulges/dents versus the
original's uniform small-bump "marshmallow" texture — a real, visible step
toward "designed" rather than "natural," though still fundamentally a
smooth rounded blob, not yet geometric/angular on its own.

### Stage 2 — Voronoi/cellular basis for configuration B

First attempt used Worley noise's F1 (distance to the nearest jittered
feature point per grid cell) directly as the height field. This failed
outright — F1 is smooth *within* each cell (a gentle dome, no
discontinuity), so it rendered as indistinguishable from a plain smooth
sphere. The standard fix is F2-F1 (distance to the second-nearest minus the
nearest): this goes to exactly 0 on a cell boundary and rises inside each
cell, giving flat-ish plates with sharp creases at the seams — the actual
"crystalline" cue. Getting this to read also needed: `smoothstep` instead of
a hard multiply+clamp threshold (a hard threshold produces creases narrower
than this mesh's ~2562-vertex spacing in places, which per-vertex
displacement geometry can't resolve at all — confirmed the same way the
palette bug below was, by finding the crease band simply wasn't being hit by
any vertex); and less domain-warping applied to this configuration than to
configuration A (heavy warping bends cell boundaries into curves and reads
as organic again, defeating the point).

With `core_morph` genuinely reaching 1.0 (see the testing-gotcha section —
earlier attempts at this were silently testing morph=0 and showed nothing
new), the result is dramatic: sharp, angular, radiating shard/spike
geometry — a real sea-urchin/shattered-crystal silhouette, the most
convincingly "alien geometric computational" result this whole prototype
has produced. Honest caveat: it currently reads as more "shattered crystal
burst" than the originally-envisioned "few large flat plates" — the F2-F1
metric's steep local gradient between adjacent cells produces sharp
*peaks*, not gentle facets, so the character is spikier/more chaotic than
"deliberate" plates. At default idle energy values this is still what
renders (see stage 3's screenshot, `core_morph` blended to 0.5) — worth
tuning down for a calmer idle state in a future pass rather than assumed
correct as-is.

### Stage 3 — Fresnel + palette tuning, combined with stages 1-2

This took far more than a color/power tweak, and the process is worth
recording because the wrong culprit was assumed twice before the real one
was found:

- First hypothesis (wrong): the noise signal driving the palette didn't
  have enough range. Ruled out by a raw grayscale visualization of the
  signal, which showed it swinging fully across its range — the palette
  still didn't show any maroon, so range wasn't the problem.
- Second finding (real, but not the whole story): the *displacement*
  signal (`primary`, a mix of na/nb) is unsuitable for driving *per-vertex
  color* even where it's fine for geometry — nb's Voronoi crease is a thin
  band that this mesh's vertices mostly don't land inside, so vertex color
  (unlike vertex-displaced geometry) rarely shows it at all. Fixed by
  giving the palette its own dedicated, higher-frequency noise sample
  (`palette_field`, sampled at 2.4x instead of geometry's 0.85x) instead of
  reading off `na` or `primary` — geometry wants low frequency for "few
  large forms," palette needs enough spatial frequency that a fixed camera
  typically sees more than one lobe (a raw grayscale check at low
  frequency showed the *entire visible hemisphere* landing inside a single
  lobe from this fixed camera — too few total lobes existed on the sphere
  at geometry-appropriate frequencies for a typical view to ever see both
  colors).
- The actual root cause of "palette never reads," found only after both of
  the above: **the Fresnel rim's EMISSION and the material's SPECULAR
  highlight**, not the noise at all. Direct pixel sampling (not eyeballing
  compressed screenshots) showed literally zero pixels anywhere on the
  visible surface with red exceeding blue — i.e., the dark maroon ALBEDO
  was never actually visible in the final pixel color, no matter how the
  noise was tuned. A diagnostic pass with EMISSION and SPECULAR both
  zeroed and ROUGHNESS maxed immediately showed a clear maroon/white
  hierarchy. The mechanism: SPECULAR's dielectric highlight is
  achromatic — it washes a dark colored ALBEDO toward gray wherever it
  lands, and the scene's single key light put a broad glossy highlight
  across much of the visible surface at the original 0.35/0.5
  ROUGHNESS/SPECULAR. The Fresnel rim's white EMISSION did the same thing
  by a different route, and even a small fraction of either brought back
  was enough to erase the maroon again (pixel count went from thousands of
  red-biased pixels back to zero).

Fix: SPECULAR → 0, ROUGHNESS → 1.0 (fully matte — this scene has no
reflection-worthy environment anyway), and the Fresnel rim's contribution
**masked by the palette itself** (`rim_color = color_white * fresnel *
structure_n`) so it brightens the already-white regions' silhouette without
bleeding onto the maroon structural regions. `color_maroon` darkened from
the original (0.28, 0.05, 0.08) but *not* as dark as a mid-iteration attempt
(0.10, 0.015, 0.03) — that attempt's color was dark enough that its hue
became imperceptible on its own, before any lighting was even applied;
(0.20, 0.035, 0.06) survives the reduced EMISSION/SPECULAR budget without
losing its hue. Verified by direct pixel sampling, not appearance alone:
thousands of visible pixels with red exceeding blue, versus zero before the
fix.

Real screenshot result: the palette hierarchy now clearly reads at a
glance — near-white body, dark maroon (reading as near-black in shadow,
genuinely warm-toned where lit) at structural creases/lobes, no longer
"barely visible." Honest caveat: the current character is high-contrast and
somewhat binary ("dalmatian-spotted" / cut-gemstone-like) rather than a
softer graceful hierarchy — a legitimate, deliberate-looking result, but a
different aesthetic than originally envisioned, and one more iteration on
the contrast curve and patch scale could soften it further if a subtler
look is wanted. Also incidentally fixed: the original prototype's
overexposure problem at high intensity/turbulence (see stage 4) — the
matte, non-additive-emission-heavy material doesn't blow out the same way.

### Stage 4 — parameter responsiveness re-check

Re-verified against the new geometry/material, using the corrected
`energy_model.gd`-editing method (see the testing-gotcha section):

- **Gold/`symbol_reveal` restraint**: still works exactly as before — small,
  sparse, warm speckles, never a wash of gold.
- **High intensity/turbulence/activity push** (0.85/0.9/0.7): no longer
  overexposes to white the way the original did — the palette hierarchy
  stayed visible even pushed hard. A genuine improvement, not just a
  side-effect noted in passing.
- **Coherence sweep (organized vs. chaotic)**: this is a real regression,
  reported honestly rather than glossed over. At `core_morph = 0.5`
  (Voronoi contributing), coherence = 0.05 and coherence = 0.95 produced
  near-indistinguishable results — the effect that worked clearly in the
  original prototype is now much weaker. Isolated to config-A-only
  (`core_morph = 0.0`, matching the original's own test conditions): still
  weaker than before, though present. The cause is directly traceable to
  stage 1's own change — narrowing the warp-amount range (1.4-0.35 →
  0.85-0.25) to keep coherence's warp from dissolving the new, larger
  lobes also shrank the absolute difference the coherence slider can
  produce. This is a real trade-off this pass introduced, not a fluke, and
  is flagged in `core.gdshader`'s own comments at the `warp_amount` line
  for the next person tuning this.

### Stage 5 — performance re-measurement

Measured the same way as the original baseline (`perf_monitor.gd`,
`perf_log.txt`, real windowed run at default parameters, not estimated):
steady-state **~1960-2050 FPS (~4.4-5.6 ms/frame)**, essentially unchanged
from the original's ~1800-2000 FPS baseline despite the added Voronoi
noise (a 27-cell neighborhood search per sample) and the extra dedicated
palette noise sample. This GPU has enormous headroom at 2562 vertices; the
extra noise cost is not currently a bottleneck. No conclusions about the
eventual full orb's performance should be drawn from this — same caveat as
the original baseline.

### Honest overall verdict

**Better, not solved.** Measured against the original "looks like a blob"
finding: the default/idle state (screenshots in this section, `core_morph`
near 0) now shows genuinely fewer, larger, more deliberate lobes with a
clearly-reading maroon/white hierarchy — a real, verified improvement, not
a relabeled version of the same problem. Pushed toward the Voronoi
configuration (`core_morph` toward 1), the result is the most convincingly
"alien geometric computational" shape this prototype has produced — sharp,
angular, radiating shard geometry, not organic at all. But: the Voronoi
result is spikier/more chaotic than the "few large deliberate plates"
originally envisioned, the palette's current character is high-contrast and
somewhat binary rather than a graceful hierarchy, and the coherence
parameter's organized-vs-chaotic effect is now noticeably weaker than
before, a real trade-off from taming configuration A's warp range. None of
these are "still looks like a blob" — that finding is resolved — but none
of them are "fully realized as designed" either.

### Updated recommendation

Good enough to keep building on for further iteration, not good enough to
treat as final. Before adding rings/wisps/particles on top: (1) tune the
Voronoi configuration's amplitude down for idle states specifically (scale
displacement by `activity`/`intensity` rather than a flat constant) so
"calm" doesn't look this dramatically spiky — currently the idle default
already shows meaningful crystalline character, which may be desirable but
should be a deliberate choice, not an accident of the current constants;
(2) either accept the current palette's high-contrast "dalmatian" character
as the intended look, or spend one more pass softening the contrast
curve/patch scale if a subtler hierarchy is wanted; (3) decide whether
coherence's weakened effect needs recovering (e.g., a separate, wider warp
range applied only where it doesn't threaten configuration A's lobe
coarseness) or is an acceptable trade-off given the Voronoi configuration's
own strong organized/chaotic character now covers some of the same ground.
Item (3) turned out to matter more than expected — see section 18.

## 18. State-personality validation — do STATE_PROFILES deliver coherent personalities?

A follow-up task validated the core architectural premise from
`JAIRUS_ORB_VFX_TECHNICAL_ARCHITECTURE.md` §1/§12: that a shared `EnergyModel`
driving every visual consumer produces *one coherent system changing*, not
several unrelated sliders moving independently. Scoped to
`prototype/orb_foundation/` only — no particles/wisps/rings/new visual
layers, no window/transparency changes, no changes to the core geometry/
shader from section 17's pass (none were needed; see the one exception noted
below).

### What was built

- **`STATE_PROFILES`** (`energy_model.gd`): a `const Dictionary` naming all 7
  real Jairus states, reusing this exact term from the archived design
  brief (`archive/orb_v1/docs/JAIRUS_ORB_VISUAL_DESIGN_DIRECTION.md` §13,
  which specified "all state tuning should remain centralized in the
  existing `STATE_PROFILES` system"). Each entry is a target vector across
  all 8 `EnergyModel` parameters plus a `camera_drift` bool (not a shader
  parameter — applied directly to `CameraRig` because `OFFLINE` needs to
  read as inactive, not "`IDLE` but dimmer," and `CameraRig`'s own
  activity-based amplitude modulation never reaches zero on its own — a
  real, separate finding, see below).
- **`EnergyModel.set_state(name)`**: looks up the profile and calls the
  existing per-parameter setters — it does not snap `current_*` values.
  The already-existing per-parameter smoothing rates (fast/medium/slow, set
  in section 17's predecessor work and unchanged here) carry the transition,
  which is *the* mechanism being validated, not new logic.
- **`state_changed` signal**: emitted at the end of `set_state()`, including
  when `SUCCESS`'s own 2-second timer calls it internally to auto-revert to
  `IDLE`. `debug_ui.gd` listens for this instead of updating its own
  label/sliders only from the button press that triggered it — this was a
  real bug caught during testing (see below), not a preemptive nicety.
- **Debug UI**: one button per state (2-column grid) plus a live "State:
  NAME" label, wired to `set_state()`. Existing sliders still work
  independently and now stay in sync with whichever state is active.
- **A scripted-capture test harness** (`debug_ui.gd`, cmdline-arg driven:
  `--state=`, `--switch=NAME:t[,...]`, `--shots=path:t[,...]`): this
  machine's window `always_on_top` flag proved unreliable against other
  foreground windows during this pass (an OS-level window compositing
  quirk, consistent with the transparency regression already documented
  elsewhere in this project — not something to re-litigate here), so
  OS-level screen capture kept racing window z-order. The harness instead
  captures Godot's own live viewport texture (`get_viewport().get_texture()
  .get_image().save_png()`) on a deterministic in-engine clock, sidestepping
  window z-order entirely — still a real, live-rendered screenshot, not a
  fabricated one, just captured through a different, more reliable API for
  this specific testing need.

### Reasoning per state (parameters: intensity / activity / turbulence /
coherence / core_morph / field_strength / particle_activity / symbol_reveal)

- **`IDLE` — 0.3 / 0.2 / 0.15 / 0.65 / 0.1 / 0.4 / 0.15 / 0.0.** Low
  intensity and turbulence for "calm"; coherence held moderately high
  (0.65, above the dataset's midpoint) for "elegant, controlled" rather
  than sluggish or messy; `core_morph` kept low (0.1) so the geometry stays
  close to configuration A's smooth coarse lobes — deliberately *not* zero,
  so there's a faint hint of the crystalline configuration even at rest,
  matching "mysterious" over "inert."
- **`LISTENING` — 0.5 / 0.45 / 0.25 / 0.8 / 0.25 / 0.55 / 0.4 / 0.12.**
  Coherence is the deliberate signature parameter here (0.8, the highest of
  any non-`SUCCESS` state) — both source docs specifically call out
  "energy becoming convergent/organized" as this state's mechanism, so
  coherence rises sharply relative to `IDLE` while intensity/activity only
  rise moderately. `symbol_reveal` gets its first non-zero value (0.12) for
  "gold beginning to appear."
- **`THINKING` — 0.7 / 0.75 / 0.75 / 0.55 / 0.55 / 0.7 / 0.7 / 0.05.**
  Turbulence pushed high (0.75) for "complex computational activity," but
  coherence deliberately held at a *middle* value (0.55) rather than
  dropped — this is the direct test of "high turbulence but still
  structured, not chaotic" the task asked for.
- **`EXECUTING` — 0.95 / 0.9 / 0.85 / 0.9 / 0.8 / 0.9 / 0.9 / 0.3.** Max
  intensity/activity/field_strength/particle_activity per both source docs.
  Coherence set *higher* than `THINKING` (0.9 vs 0.55) even though
  turbulence is also higher — this is the brief's own explicit formula for
  "overwhelming power under perfect control," tested directly rather than
  approximated. `symbol_reveal` at a moderate 0.3 (the source table flags
  this as "context-dependent"; reasoned as "partially visible while
  actively working," reserving a fuller reveal for `SUCCESS`).
- **`SUCCESS` — 0.55 / 0.3 / 0.15 / 0.85 / 0.15 / 0.45 / 0.35 / 0.9.**
  Turbulence and `core_morph` drop back toward `IDLE`'s resting values
  ("clean synchronized resolution," not more computation), coherence
  briefly high (0.85, matching the source table's "max, briefly"),
  `symbol_reveal` high (0.9) for the gold highlight, and `trigger_pulse()`
  is called once on entry. This profile is inherently transient — `set_state`
  starts a 2-second timer that auto-reverts to `IDLE` when it fires, modeling
  "settles back toward idle's baseline" testably without a real state
  controller.
- **`ERROR` — 0.35 / 0.4 / 0.5 / 0.15 / 0.4 / 0.3 / 0.25 / 0.0.** No color
  parameter exists to misuse here by construction — the only lever is the
  same 8 numbers every other state uses. Coherence is the deliberate
  signature (0.15, the lowest of any state) — this is the mechanism the
  brief specifies for expressing failure without a red/danger trope.
  `core_morph` was deliberately set close to `THINKING`'s value (0.4 vs
  0.55) with everything else reduced, specifically to test whether
  coherence *alone* can differentiate "controlled intensity" from
  "uncontrolled failure" at similar underlying geometric structure — see
  the honest finding below on how well this worked.
- **`OFFLINE` — 0.08 / 0.0 / 0.0 / 0.6 / 0.0 / 0.05 / 0.0 / 0.0,
  `camera_drift: false`.** Not literally all-zero (`intensity` at 0.08) so
  the object still faintly exists rather than vanishing, matching the
  source doc's flagged-open "still exists, just dormant" question — resolved
  here in favor of a faint presence. `activity`/`turbulence` at exactly 0
  (`IDLE` keeps a nonzero 0.15/0.2) is the main lever distinguishing this
  from "`IDLE` but dimmer": nothing moves at all. `camera_drift: false` is
  the other lever — needed because `CameraRig`'s activity-based amplitude
  modulation (`camera_rig.gd`) only *scales* the drift amplitude between
  1.0x-1.6x of a constant 4° base; it never reaches zero on its own even at
  `activity = 0`, contradicting `JAIRUS_ORB_VFX_TECHNICAL_ARCHITECTURE.md`
  §14's stated intent ("at zero amplitude, effectively frozen"). This is a
  real, minor mismatch between that document's intent and `camera_rig.gd`'s
  actual implementation, found during this pass — not fixed here (out of
  scope: `camera_rig.gd` itself wasn't touched), worked around instead by
  having `set_state()` toggle `drift_enabled` directly, which was already an
  exposed, intended-for-exactly-this-purpose property.

### Honest per-state screenshot findings (all at rest, after settling)

- **`IDLE`**: reads as reasonably calm — smooth-ish coarse lobes, subdued
  energy. Weaker than intended on "elegant/mysterious" specifically because
  the palette's high-contrast mottled pattern (fixed shader constants from
  section 17's pass, not driven by any `EnergyModel` parameter) looks
  identical in *character* at every state, just dimmer — a genuinely calm
  object would likely want a quieter, less "busy" surface marking at rest,
  and nothing in the current architecture varies that. Real, honest gap.
- **`LISTENING`**: unexpectedly spiky/faceted for a state whose `core_morph`
  (0.25) is mostly configuration A. Root cause, confirmed by comparing
  against `IDLE`/`OFFLINE` (both `core_morph` <= 0.1, both genuinely
  smooth): the Voronoi configuration's F2-F1 edges are *sharp-slope*
  features — even blended in at a 25% weight, their local shading gradient
  (which is what a viewer actually perceives) is disproportionate to their
  blend-weighted displacement amplitude, because shading responds to slope,
  not height. A small amount of Voronoi reads as "a lot more crystalline"
  almost immediately once `core_morph` leaves 0. This is a real,
  previously-undiscovered property of the section 17 shader work, not a bug
  in this pass's profiles — `core_morph` is not a perceptually linear
  "calm-to-spiky" dial the way its numeric range suggests.
- **`THINKING`**: more intense/bright version of the same spiky character —
  a real escalation from `LISTENING`, but the shape *language* doesn't
  progress much further than `LISTENING` already showed; most of the
  visible change between these two states is brightness, not form.
- **`EXECUTING`**: brightest, most maximal — clearly "more" than
  `THINKING`. But scrutinized specifically against "must read as controlled,
  not dangerous": genuinely ambiguous. The dense radiating shard silhouette
  could plausibly read as "cut gemstone" (controlled) or "urchin/burst"
  (aggressive) depending on the viewer, and — this is the important
  finding — the parameter that's supposed to resolve that ambiguity in the
  brief's own design (`coherence`, 0.9 in `EXECUTING` vs. 0.55 in
  `THINKING`) does **not** produce a clearly perceptible difference between
  the two states' screenshots. This directly confirms, with a concrete
  visual consequence, the coherence-response regression section 17 already
  flagged as a side effect of narrowing the warp-amount range — it isn't
  just a slider that moved less than before, it's specifically undermining
  the brief's stated mechanism for `EXECUTING`'s single most important
  constraint. **This is the most significant finding of this pass.**
- **`SUCCESS`**: works well — visibly rounder/calmer silhouette than the
  `THINKING`/`EXECUTING` cluster (matching its low `core_morph`), with
  clearly visible scattered gold speckling. Reads as a genuine, distinct
  "resolving" moment.
- **`ERROR`**: no red, confirmed — stays entirely in the established
  maroon/white/gray palette. Reads as dim and irregular/asymmetric relative
  to `EXECUTING`, which is the intended mechanism working as designed at
  the silhouette level. Whether a cold viewer (no context that this is an
  "error") would specifically read "something is wrong" rather than just
  "a different, spikier rock" is genuinely unclear — plausible, not
  certain. Partial success: clearly avoids the red-danger cliché (the
  explicit constraint), clearly distinct from other states, less clearly a
  confident "reads as failure" on its own without contextual priming.
- **`OFFLINE`**: works well and unambiguously — much dimmer, visibly
  smoother/static geometry, frozen camera. The clearest success of the
  "must be distinct from its nearest neighbor" tests in this pass (`IDLE`
  vs. `OFFLINE`), because it had two independent, both-working levers
  (energy parameters *and* camera stillness) rather than relying on one.

### Transition-quality findings

Two sequences captured (`IDLE`→`EXECUTING`, `EXECUTING`→`ERROR`), 5 frames
each at increasing elapsed time after the switch. Both read as **one
continuously-changing system, not a jump cut**: `IDLE`→`EXECUTING` shows
spikes first emerging at the silhouette edge, then propagating inward as
brightness climbs, arriving at the full radiating-burst look over roughly
1.5-2 seconds; `EXECUTING`→`ERROR` shows intensity visibly dropping frame
by frame while the shape lags slightly behind (matching the fast/medium/slow
per-parameter smoothing rates being genuinely different, not a single
uniform lerp), settling into the dimmer, more irregular `ERROR` silhouette
by ~3 seconds. This is a clear, confirmed win for the architecture: staggered
per-parameter smoothing produces a transition that looks organic rather
than mechanical, exactly the property section 12 of the technical
architecture doc predicted from this mechanism.

### `field_strength` / `particle_activity` honesty check

**Confirmed fully inert, plainly stated**: both are declared as global
uniforms, smoothed by `EnergyModel`, and pushed to the shader every frame
exactly like the other 6 parameters — but `core.gdshader` (the only shader
driving a visible object in this prototype) never reads either one.
`grep`-confirmed, not assumed. Every `STATE_PROFILES` entry still sets
reasonable target values for them (matching the source table's per-state
guidance), because `EnergyModel` is the correct place to own that data
regardless of whether a consumer exists yet — but no screenshot in this
report shows any visual difference attributable to these two parameters,
because none currently exists to show. This will only become a meaningful
test once an energy-field shell or particle system is built.

### FPS check

Measured with active state switches occurring *during* the sample window
(`EXECUTING` at t=2s, `ERROR` at t=5s, `THINKING` at t=8s, one sample/sec
throughout): steady **~1950-2060 FPS**, matching section 17's ~1960-2050 FPS
baseline with no dip during any transition. `set_state()` and the
`state_changed` signal are trivial-cost (a dictionary lookup and a handful
of float assignments, once per state change, not per frame) — no
performance regression, confirmed rather than assumed.

### Overall verdict — does the architecture deliver?

**The core architectural premise is validated; the full 7-personality goal
is not yet fully delivered, and the gap has an identifiable cause.**

The thing this task actually set out to test — does a shared `EnergyModel`
produce *one coherent system changing*, with every aspect (geometry,
palette, camera) moving together in a way that reads as one living object
rather than independent sliders — is a clear **yes**, demonstrated
concretely: the transition sequences show real, staggered, organic-feeling
interpolation across multiple simultaneously-changing aspects, driven by
nothing more than changing 8 target numbers in one place. That premise does
not need particles/wisps/rings to be fairly judged; it was fairly judged
here, using only what exists, and it holds up.

What doesn't yet fully hold up is the *personality* goal specifically:
`IDLE`, `SUCCESS`, `OFFLINE`, and to a good extent `ERROR` read as genuinely
distinct, coherent personalities. `LISTENING`, `THINKING`, and `EXECUTING`
collapse toward a similar "spiky crystalline burst, differing mainly in
brightness" character, for two identifiable, non-mysterious reasons: (1)
`core_morph` is not a perceptually linear dial, so any state with
meaningfully nonzero `core_morph` already looks dramatically more
crystalline than the numeric value alone suggests; (2) `coherence`'s
response was measurably weakened by section 17's own warp-range change,
which specifically undercuts `EXECUTING`'s brief-mandated "high coherence =
controlled power" mechanism — the single most load-bearing parameter choice
in the entire state-profile design doesn't come through clearly. Both
causes are diagnosed, specific, and fixable within the existing core shader
(not architecture) — this is a tuning problem in section 17's noise/shading
work, not evidence the shared-parameter architecture itself doesn't work.
**Recommendation**: before adding any new visual layer, spend one more
focused pass on exactly these two shader-level issues (core_morph's
non-linearity, coherence's range), since they're what's actually preventing
the full personality goal from landing — not the absence of particles or
wisps.

**Both fixed in a follow-up pass — see section 19.**

## 19. core_morph linearity + coherence range fix

A targeted shader-math fix for section 18's two diagnosed root causes —
deliberately not a new exploration. Scoped to `core.gdshader` and
`energy_common.gdshaderinc` only; the 7 `STATE_PROFILES` values themselves
were not touched (confirmed via `git diff` — the fix had to make the
*existing* committed values produce correctly differentiated results, not
require new values to compensate for a shader bug).

### Fix 1 — core_morph perceptual linearity

**Root cause, confirmed, not just theorized**: `primary = mix(na, nb,
morph)` mixes a smooth field (`na`, low slope everywhere) against a
near-binary one (`nb`, the Voronoi F2-F1 edge metric — flat cell interiors,
razor-sharp slope at a fixed-width crease regardless of blend weight).
Shading responds to slope, not blended height, so scaling a sharp crease's
*height* down to 10% by a low `morph` barely softens its *slope* — the
crease was still just as narrow, just shallower, and a shallow-but-narrow
crease still throws a hard shading edge. The blend weight was linear; the
crease's own sharpness was constant. That mismatch is what made a small
`core_morph` value look disproportionately crystalline.

**Fix**: made the crease's own width a function of `morph`, not just its
blend weight. A new `voronoi_edge_width_soft` uniform (0.42, versus the
existing sharp `voronoi_edge_width` at 0.12) is the transition width used
at `morph = 0`; `effective_edge_width = mix(voronoi_edge_width_soft,
voronoi_edge_width, morph)` narrows it toward full sharpness only as
`morph` rises. Now a low `morph` blends in a *genuinely soft* version of
the Voronoi field (wide transition = low slope), not a permanently-sharp
feature merely downweighted — both the crease's sharpness and its blend
weight ramp together.

**Verified at all 5 requested intermediate values** (0.1/0.25/0.5/0.75/1.0),
coherence held at 1.0 to isolate this fix from Fix 2's own contribution,
same camera/lighting throughout (real screenshots, `fix_shots/morph_0*.png`):
0.1 — smooth, no visible facets, matching `IDLE`'s intended read. 0.25 —
visibly bumpier/craggier, a real step up from 0.1, but nothing like the
previous pass's near-full spike burst at this value. 0.5 — clearly faceted
and jagged, a further real step, still short of a full burst. 0.75 — close
to the full crystalline-burst character. 1.0 — full burst, matching the
pre-fix endpoint (the fix only changes the *path* between 0 and 1, not the
endpoints, by construction — `effective_edge_width` converges to the
original sharp value at `morph = 1`). Honest note: the progression is not
perfectly linear — the escalation from 0.5 to 0.75 is steeper than from 0.1
to 0.5 — but the specific bug (an early cliff where 0.25 already looked
almost as extreme as 0.8) is gone, confirmed at the exact intermediate value
the previous pass flagged.

### Fix 2 — coherence's own lever

**Root cause, confirmed, not just theorized**: section 17's coarser-
deformation pass narrowed `warp_amount`'s range (1.4-0.35 → 0.85-0.25) so
low coherence's domain warp wouldn't dissolve configuration A's larger
lobes back into mush — a correct, deliberate fix for that specific problem.
Its side effect: `warp_amount` was coherence's *only* lever, so narrowing
its range also narrowed how much visual difference coherence alone could
produce.

**Fix**: gave coherence a second, independent lever rather than re-widening
`warp_amount` (which would have undone section 17's own fix). A new
mid-frequency noise layer (`p * 4.5`, distinct from both the geometry-basis
frequencies and the `turbulence`-driven `fine` layer) is added directly to
the displacement, scaled by `coherence_noise_amplitude` (0.16) times
`(1 - coherence)`. High coherence suppresses it to ~0 (clean surface); low
coherence adds a visibly rough, grainy texture on top of whatever shape is
underneath, completely independent of `core_morph`, `turbulence`, or
`warp_amount`. `warp_amount`'s range is untouched — confirmed via `git
diff` on that specific line.

**Verified against the exact committed `THINKING` (turbulence 0.75,
coherence 0.55) and `EXECUTING` (turbulence 0.85, coherence 0.9) profiles**,
no new tuning (`fix_shots/fixed_THINKING.png`, `fixed_EXECUTING.png`):
there is now a real, visible difference. `EXECUTING` reads as brighter and
notably *cleaner* — smoother facet faces, less surface grain. `THINKING`
shows visibly more roughness/grain across its surface from the added noise
term (at coherence 0.55, `coherence_noise_amplitude * (1-0.55) ≈ 0.072` —
a modest but genuinely visible contribution). Honest characterization: the
difference this fix produces is about surface *cleanliness/grain*, not a
dramatic reorganization of overall silhouette symmetry — a viewer expecting
"coherence = more symmetric shape" specifically (rather than "coherence =
smoother surface") might still find the distinction subtle between these
two particular states. It reads far more clearly between `EXECUTING` and
`ERROR` (coherence 0.9 vs. 0.15 — near the mechanism's full range), where
`ERROR`'s surface is unambiguously rough/grainy/disorganized against
`EXECUTING`'s clean faceted look.

### Full 7-state re-test (same profiles, unchanged)

Direct comparison against section 18's "collapse toward similar" finding:

- **`EXECUTING`**: brightest, most maximal, and — per Fix 2 — visibly

Two isolated, switchable comparison scenes (not a merged system), each

### Stage 1 — both candidates alone, static test

Launched via the project's existing capture harness
(`Godot_v4.7.2-stable_win64.exe --path <project> res://wisp_test_X.tscn
--state=THINKING --shots=<path>:<t>`, same mechanism prior passes used) at

- **Candidate A**: real screenshot shows the core rendering correctly, and
  — after inspection — two faint, barely-visible white slivers near the
  bottom edge. No visible flowing trail geometry, no "many small organic
  currents" read.
- **Candidate B**: real screenshot shows a clearly visible white ribbon arc
  sweeping around the core's right/top silhouette, plus a fainter gold arc
  partially visible past the debug panel. Reads immediately as an
  intentional energy current, not a rendering accident.

This asymmetry was surprising enough (Candidate A should be the *cheaper,
easier* technique per section 11's own table) that it was investigated
before accepting it, rather than assumed to be a tuning miss.

### Root cause: Candidate A is not a tuning problem, it's a renderer incompatibility

This project's `project.godot` sets `renderer/rendering_method="mobile"`
(confirmed active at runtime — every test run's log line reads `Vulkan
1.4.351 - Forward Mobile`; the `rendering_method.mobile="gl_compatibility"`
line is a platform feature-tag override that only applies when *exported
to* a mobile OS, not on this desktop dev machine). A web search (`Godot 4
GPUParticles3D trail_enabled Compatibility renderer support`, and a
follow-up specifically on the Forward Mobile renderer) turned up a
real, documented Godot limitation, corroborated across multiple
independent sources including Godot's own GitHub issue tracker: **the
Mobile and Compatibility renderers do not support the compute-shader path
`GPUParticles3D`'s `trail_enabled` requires, so trail vertices are never
generated — the particle system silently falls back to rendering only the
bare head-particle mesh, with no error or warning.** That is a precise,
mechanistic match for what the screenshots showed: `RibbonTrailMesh`
instances rendering as tiny static slivers at each particle's current
position, never extruded into an actual trail.

Confirmed directly, not just inferred from the search: a diagnostic run
with `Core.visible = false` (temporary, scratch-only scene, not committed)
at `EXECUTING` (`particle_activity=0.9`, the densest state) isolated the
wisps alone. Of 3 emitters × 24 particles (up to ~65 particles visible at
that `amount_ratio`), only 2-3 tiny disconnected slivers rendered anywhere
on screen — real, measured evidence of the failure, not assumption.

A CPU-side fallback was tried before giving up on the technique family:
`CPUParticles3D` doesn't depend on compute shaders, so it was worth
checking whether it could deliver the same trail character. Real result: a
script error — **`trail_enabled` is not a valid property on
`CPUParticles3D` at all** in Godot 4.7; trails are a `GPUParticles3D`-only
feature, with no CPU-side equivalent. This closes off the fallback
cleanly: in this project, on this renderer, there is no way to get real
`GPUParticles3D`/`CPUParticles3D` trail geometry without switching the
renderer to Forward+, which is out of this task's scope (it would affect
the already-validated core's rendering path project-wide, not just wisps).

Screenshots captured at `IDLE`, `THINKING`, and `EXECUTING` for both
candidates, same camera/lighting, core visible:

- **Candidate A**: at `IDLE` (`particle_activity=0.15`), zero wisps visible
  at all. At `EXECUTING` (`particle_activity=0.9`, the theoretical densest
  case), still only 2-3 faint slivers — confirms the failure is constant
  across the whole parameter range, not just a low-activity visibility

- **Candidate B**: at both `IDLE` and `EXECUTING`, all 3 hero ribbons
  render correctly and consistently. The per-state *brightness* difference
  (shader's `EMISSION` scales roughly 0.69→1.5 from `IDLE`'s to
  `EXECUTING`'s `energy_intensity`) is real in the shader math but subtle
  in a static, non-HDR PNG comparison — genuinely hard to confirm from a
  still screenshot alone; the flow-*speed* difference (`energy_activity`
  drives `flow_speed` from 0.15 to 2.5) is animation-only and can't be
  judged from a static frame at all. Both would need live observation to

A follow-up pair of clean screenshots (debug panel hidden via a

### Cost comparison, real numbers (6-second soak at `EXECUTING`, same test conditions, `vsync_mode=0`)

| | Steady-state FPS | Primitives (total incl. core) | Wisp-only primitives (core subtracted) | Draw calls |
|---|---|---|---|---|
| Candidate A | ~1900-1970 | ~25,570 | ~20,450 | 54 |
| Candidate B | ~2010-2120 | ~7,710 | ~2,590 | 54 |

Candidate A costs roughly **8x** the primitives of Candidate B for a

### `EnergyModel` integration cleanliness

Matches section 12's own architectural distinction: Candidate B is a pure
shader consumer (`wisp_hero_ribbon.gdshader` reads `energy_activity`/

per-frame script coupling, zero references to `EnergyModel` at all).
Candidate A needs a `_process()` in `wisp_system_a.gd` that reads
`EnergyModel` directly every frame, because `GPUParticles3D`'s

consumers" case section 12 already calls out. Both integrate correctly
with the *existing* single-source-of-truth parameters (no second parameter
source introduced either way), but Candidate B's integration is
structurally simpler.

### Decision

**Candidate B — static `Curve3D`-built hero ribbons with shader-driven
flow — wins outright.** This is not a re-statement of section 11's a
priori hybrid reasoning; it's a decision made from real evidence gathered
in this exact project: Candidate A is not merely worse, it is **non-
functional** under this project's actual active renderer (Forward Mobile),
for a real, documented, verified reason (no compute-shader trail support),
with no viable same-technique-family fallback (`CPUParticles3D` doesn't
support trails at all). Candidate B renders correctly, looks intentional,
stays visually subordinate to the core, costs an order of magnitude fewer
primitives, and integrates more simply with `EnergyModel`.

**The doc's suggested hybrid (section 11) is explicitly NOT the right
answer for this project as written.** Mixing a working technique with one
confirmed broken in this exact rendering configuration isn't a hybrid,
it's shipping half a broken system. If a future pass wants a second,
stochastic population of smaller/secondary wisps alongside Candidate B's
hero currents (closer to the brief's original "hero + secondary" framing),
it would need to use plain `GPUParticles3D` billboards *without*
`trail_enabled` (ordinary GPU particle simulation works fine under Forward
Mobile — only the trail-compute-shader path is broken), not the
trail-based approach section 11 originally proposed for that role. That is
a real, separate follow-up question, not something this pass tried to
answer.

### Honest read: does Candidate B achieve "field currents, not fantasy magic"?

Yes, on the evidence gathered. The 3 hero ribbons read as deliberate energy

next verification step, not claimed as done here.

### Verdict on readiness to build further on

**Ready.** The decision is made from real, verified evidence (not
re-stated a priori reasoning), the core is confirmed completely unaffected

### Real mistakes this pass made and fixed, with screenshot evidence (reported honestly, not smoothed over)

Two genuine bugs were caught by real screenshots during this pass, not
assumed away:

1. **Ring orientation.** First attempt tilted the rings only slightly from
   what was assumed to be an edge-on default — the resulting screenshot
   showed both rings as thin diagonal lines crossing the core, not
   recognizable halos. An isolated diagnostic (opaque high-contrast
   placeholder shader, no other geometry) proved the opposite: `TorusMesh`'s
   *default* orientation already faces this scene's camera; a large
   "correction" toward 90 degrees actually turned a working ring into a
   genuinely edge-on, invisible one. Root cause of the *original* thin-line
   look turned out to be radius, not orientation (next point).
2. **Additive blending vs. this project's transparent window.** Both
   shaders were first written with `render_mode blend_add` for its
   order-independent-transparency property. A real screenshot of an
   isolated scene (rings only, zero opaque geometry) rendered **completely
   blank** despite verified-correct geometry — this project's per-pixel-
   transparent viewport writes near-zero alpha wherever *only* additive
   geometry covers a pixel, so the rings were only ever visible where they
   happened to overlap the opaque core, never against plain background.
   Fixed by switching both shaders to `render_mode blend_mix`, matching
   `wisp_hero_ribbon.gdshader`'s already-proven pattern from section 20.

Both fixes are documented in-line in `structural_lattice.gd` and the two
shader files' own comments, not just here, so a future pass doesn't
re-discover the same failure modes from scratch.

### Stage 1 — lattice alone, shells alone (static test, core visible)

**Lattice**: real screenshot (`EXECUTING`, both with and without the debug
panel) shows two clearly distinct elliptical ring halos wrapping the core
at different apparent angles, dim relative to the core's own emission,
reading as intentional orbital structure — not competing with the core.

**Shells**: real screenshot shows two distinct Fresnel-rim halos at
different radii around the core immediately, no orientation issues (a
sphere has no meaningful "default orientation" problem the way a torus
does) — inner shell reads as a tighter, brighter rim; outer shell reads as
a softer, dimmer, wider halo. This is the falloff-gradient differentiation
`energy_shell.gdshader` was built for, not two equally-bright nested
copies — confirmed visually, not just by the parameter values used.

### Stage 2/3 — overdraw check (real numbers, Viewport overdraw debug mode, not FPS)

Measured with `overdraw_probe.gd`'s `DEBUG_DRAW_OVERDRAW` average-brightness
proxy, same camera/state (`EXECUTING`) across four scenes:

| Scene | Avg. overdraw brightness | Relative to core baseline |
|---|---|---|
| Core only (`core_baseline_test.tscn`) | 0.0469 | 1.0x (reference) |
| Lattice + core (`lattice_test.tscn`) | 0.0979 | ~2.1x |
| Shells + core (`shells_test.tscn`) | 0.2661 | ~5.7x |
| Full combined (core+wisps+lattice+shells, `full_scene_test.tscn`) | 0.2684 | ~5.7x |

Honest reads on these numbers:

- **The energy-field shells are overwhelmingly the dominant overdraw
  cost**, not the lattice and not the wisps. Full-combined overdraw
  (0.2684) is barely above shells-alone (0.2661) — wisps and lattice
  together add less than 1% on top of what the two shells already cost.
  This matches section 16's own prediction exactly ("overdraw from layered
  transparency... the #1 thing to measure early") and confirms *why*
  section 5/18's "small fixed shell count" rule is the real lever here,
  not shell material complexity or the other systems.
- **No numeric budget exists to compare this against** (confirmed above —
  the doc never states one), so "within budget" can only be judged against
  the doc's actual qualitative rule: keep the shell count small and fixed.
  This pass built exactly 2 shells, matching section 6's own concrete
  spec, not 3 (section 4's upper bound) and nowhere near V1's discarded
  4-shell design.
- The raw `DEBUG_DRAW_OVERDRAW` screenshots themselves are hard to read
  visually in this project's specific transparent-window setup (the
  core's own silhouette renders unexpectedly faint in that debug mode,
  likely a transparent-viewport-specific interaction with Godot's debug
  draw pipeline, not investigated further since it doesn't affect the
  numeric proxy's validity) — the *numbers* are the real measurement here,
  not the pictures, and they're internally consistent and monotonically
  increasing exactly as expected (core < lattice < shells ≈ full).

### Stage 4 — full combined scene, 3 states, core/wisps not buried

Real screenshots (`IDLE`, `THINKING`, `EXECUTING`, plus one clean/no-panel
shot at `EXECUTING`) of `full_scene_test.tscn` (core + Candidate B wisps +
lattice + shells together):

- The core's already-validated per-state distinctness (smooth/calm at
  `IDLE`, faceted/organized at `THINKING`, maximally spiky/crystalline at
  `EXECUTING`) remains clearly the dominant visual read in every shot —
  not diminished or muddied by the new layers.
- The wisp hero currents (white + gold arcs) remain clearly visible in
  every shot, distinguishable from the lattice rings by their meandering,
  non-planar path vs. the rings' clean elliptical shape.
- Both lattice rings are clearly visible as distinct halos at different
  angles in every shot.
- The shells are present but genuinely subtle at this zoom level — they
  read as a soft brightening right at the core's silhouette edge rather
  than a distinctly separate visible layer the way the lattice rings and
  wisps are. This is consistent with their low `base_alpha` (0.22/0.12)
  and the deliberate "atmosphere, not a second core" design intent, but
  it's an honest limit worth naming: at this camera distance/zoom, the
  shells contribute more to overdraw cost (per stage 2/3's numbers) than
  they contribute to legible visual distinctness. A future pass tuning
  final shell opacity should know this trade exists.

### Stage 5 — final FPS + overdraw, full combined scene

6-second steady-state soak at `EXECUTING` (`vsync_mode=0`, same measurement
method as prior passes): **~1250-1275 FPS**, down from wisps-alone's
~2010-2120 FPS and core-alone's ~1900-2100 FPS baselines (both measured in
section 20). That's a real, measured ~35-40% FPS reduction from adding the
lattice+shells — a genuine cost, not nothing, and it lines up with the
~5.7x overdraw-proxy increase measured above. In absolute terms, ~1250 FPS
unsynced still leaves roughly a 20x margin over a 60 FPS target, so this is
not a practical bottleneck *today* — but the relative cost is real and
should be tracked as particle populations (step 6) add more transparent
draws on top.

### Verdict

**Within the doc's actual (qualitative) budget, and ready to build on, with
one honest caveat.** The shell count follows section 6's own concrete
2-shell spec exactly, not V1's discarded 4-shell pattern; the two shells
are genuinely differentiated by Fresnel sharpness/opacity/parameter-weighting
rather than reading as "nested glowing spheres" (confirmed by direct
screenshot, not assumed); the lattice rings read as intentional orbital
structure once two real bugs (orientation, additive-blend alpha) were
found and fixed with evidence, not guessed at. Core distinctness and the
validated wisp system both remain clearly legible with every new layer
added. The one real, unresolved trade: shells cost more in measured
overdraw than they currently contribute in visual legibility at this
zoom/opacity — worth revisiting `base_alpha` tuning in a future pass, not
a blocker for building particle populations (step 6) next.
